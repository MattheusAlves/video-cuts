# Detailed performance plan

Status: proposed, not implemented. This document supersedes the performance mechanics in `2026-11-25-pipeline-performance.md`; the companion editing research remains applicable. Do not interrupt the current job or change its files while it runs.

## 1. What we know and what we do not

- Source `KXuTmIJmEAg` has a transcript duration of 1,146 seconds. Logs show transcription from approximately 18:58:47 to 19:04:07 (320 seconds including any preceding work between those log entries); media was reused. This is approximately 3.6x real time, not a controlled benchmark.
- The first two selector requests took 128 seconds and 72 seconds. Their mean is 100 seconds, but two observations are insufficient to forecast the remaining calls or provider reliability. At a 60-second maximum cut, windows are 180 seconds with a 120-second stride; this transcript requires ten nonempty windows if all contain speech, plus a review call when candidates exist. The previous estimate of nine windows was incorrect.
- `Select` currently executes windows serially, saves accepted candidates after each completed window, deduplicates and performs one final review. Fast mode could reduce work, but reviewing earlier or more often may add provider calls and still miss stronger moments later.
- Transcription currently invokes a CPU whisper.cpp build with the small model and no explicit thread count. The RTX 3060 Ti is available in WSL, but the CUDA toolkit/build has not been configured or measured. Renderer uses `libx264`, `veryfast`, three threads and a blurred background; no render timing is known.
- The UI serializes jobs with `runMu`; progress and job records are in memory. Existing checkpoint fingerprint depends on the transcript and selector prompt, including settings; changing prompt inputs can invalidate reuse. Raw media and transcript are cached independently. Selection currently returns multiple candidates but the pipeline renders only one.

## 2. Outcomes and guardrails

Measure time to first reviewable cut, time to requested batch completion, selector calls and errors, stage wall time, and human-rated cut quality. The primary goal is a substantial reduction in time to first useful cut, with a separate full-scan option for coverage. Record a baseline before setting any numeric product target. An experiment is adopted only when it is faster on the same inputs and does not materially reduce independently reviewed quality or reliability; define acceptable thresholds with the editor after the baseline is collected.

Never publish automatically, bypass literal hook/story validation or editorial review, alter source-relative timing, generate invented context, leak credentials, or discard valid checkpoints. Return fewer cuts when insufficient distinct candidates pass review. Clearly communicate the quality/coverage tradeoff of stopping early. Concurrency defaults to one until measured. Every optimization must be independently reversible.

## 3. Baseline and measurement (first deliverable)

**Files:** `pipeline/progress.go`, `pipeline/select.go`, `cmd/yt-short/run.go`, `cmd/yt-short/server.go`, `web/src/main.jsx`; tests beside changed code. Place benchmark results in a separate local report without transcript text or credentials.

1. Observe the current run to its natural completion or failure. Preserve its files. Capture actual full sequence from its existing log, including start/end times, cache reuse, window counts, reviewed/accepted candidates, errors, quota response, render time, and total time. If unavailable, mark fields unknown. Do not launch another copy while it runs.
2. Introduce a structured timing event with job ID, source ID/video ID, stage, start/end, duration, outcome, and `reused`; selection adds window bounds, attempt, and whether a checkpoint was used. Review has its own event. Include software/model/config fingerprints, not prompts, keys or transcript text. Use monotonic time for durations, UTC timestamps for correlation. Persist a small append-only per-job timing report with safe concurrent writes; existing UI job memory is not durable.
3. Report stages download, audio conversion, Whisper inference, transcript persistence, each selection window, review, each render, finalization. Record time to each reviewable output as well as total. UI shows stage elapsed, selection completed/total, current operation, and cached versus fresh work; show explicit error/status. No fabricated percent or ETA for provider calls. Keep logs as a secondary source.
4. Test durations and stage transitions with an injected clock/reporter, including failed/cancelled stages and cache hits. Verify persisted events survive restart and do not contain key or transcript text. Run `go test ./...`, `go test -race ./...`, and `npm run build:embedded` from `web` when available.
5. Use at least three diverse Portuguese recordings, including this one and a longer two-speaker recording. For comparisons use identical source files, candidates/settings and warm/cold cache state. Separate download from reuse. Record each run's provider/model, hardware, build, model checksum, source duration, quality review and errors. Repeat stochastic provider experiments when quota permits; do not claim significance from a single run.

## 4. Fast mode and multiple cuts (highest-leverage product change)

**Files:** `pipeline/select.go`, `pipeline/select_test.go`, `cmd/yt-short/run.go`, `cmd/yt-short/run_test.go`, `cmd/yt-short/server.go`, `cmd/yt-short/server_test.go`, `pipeline/cut.go`, `pipeline/notify.go`, `web/src/main.jsx`.

**Contract.** Add request fields `selection_mode` (`full` or `fast`) and `target_cuts` (integer, proposed 1–5, default 1). Full remains default pending quality evaluation. Validate target independently from `candidates_per_episode`: the selector must be able to return enough reviewed candidates. Explain in the UI that fast mode stops early and may miss later, stronger clips. Both modes return at most the requested number of distinct reviewed cuts; fewer is an explicit successful shortfall when the source is exhausted.

**Algorithm.** Keep full mode's ordered complete scan and final review. In fast mode process windows in source order, validate and deduplicate candidates, and review newly eligible candidates in a batch after each window that adds candidates. Accumulate accepted distinct cuts. Stop scheduling windows as soon as the accepted count reaches the target; otherwise continue until exhaustion. Do not repeatedly review unchanged rejected candidates in the same run. If review fails or quota is exhausted, report failure and retain completed work; never treat an unreviewed candidate as accepted. This proposes low time to first batch, but may increase review calls; measure it against a policy that reviews after two promising windows before choosing a default batching policy.

**Persistence and reuse.** Separate window extraction results from editorial review results. Use stable candidate IDs derived from source ID, exact normalized boundaries and relevant selection version. Record review results keyed by candidate content, transcript version, reviewer prompt/model/provider fingerprint and context; never reuse incompatible verdicts. Maintain the existing fingerprint semantics and migration tests; if compatibility cannot be proven, preserve the old checkpoint and rescan rather than overwrite it. A fast run records scanned windows individually and does not mark the remainder complete. Full mode resumes missing windows. Store state atomically and use one writer per job; handle truncated files as recoverable without inventing results.

**Rendering and recovery.** Render ranked distinct accepted candidates incrementally to unique stable paths using higher precision than current integer-second filenames. Persist a sidecar and completion marker per cut; publish atomically. A retry validates existing output and sidecar, resumes unfinished cuts and avoids duplicates. Preserve successful cuts after failures and do not mark a video fully processed or delete source media until all requested work has either completed or a scan-exhausted shortfall is recorded. Report partial success, target, accepted count and error distinctly. Avoid using the source-level `Seen` flag as the only batch checkpoint.

**Tests.** Fake provider and renderer: first window succeeds; several reviewed cuts; rejected and duplicate cuts followed by later success; target not met; zero candidates; failure in a later review/render/sidecar; restart with partial completion; changing mode, prompt, model or target; corrupted checkpoints; cancellation; overlapping boundaries; filename collisions. Assert full mode covers all windows and no rejected candidate renders. Test UI/API validation and use race tests.

**Experiment.** Replay the same existing transcript and provider setup for full scan and fast mode targets 1 and 3. Record first-cut and batch times, calls, cache hits, cost/quota, distinct clips and source positions. A human compares each against complete-scan choices and source context. Fast mode is opt-in regardless of speed until the quality tradeoff is understood. Since provider outputs are stochastic, record all results and repeat when quota permits.

## 5. Bounded provider parallelism (conditional experiment)

**Hypothesis:** two independent windows in flight may reduce wall time if the remote service allows concurrent requests; this machine's GPU will not speed up a remote call. The observed 72–128-second durations and unknown rate limits do not prove this hypothesis.

1. Inspect provider documentation and actual quota behavior before changing defaults. Benchmark concurrency 1 versus 2 on the same transcript and settings, starting from comparable empty checkpoint copies. Do not run experiments while the user's job is active. Measure wall time, per-call latency, 429/401/403, timeouts, requests actually started, token/cost data if exposed, and accepted quality. Stop on account/quota errors; do not start a request storm.
2. If supported, build a bounded worker pool with a concurrency setting 1–2, default 1. Workers receive immutable window inputs and return results to a single coordinator, which validates, orders, deduplicates and atomically writes checkpoints. Full mode's output ordering and fingerprints must not depend on completion order. Keep the current UI job-level serialization.
3. For fast mode, limit speculative in-flight work to the same bound; stop dispatching as soon as the target is reached. Cancel outstanding calls only when provider/client semantics allow; report already-started calls as possible quota use. Preserve completed results. Define deterministic selection using source order, not whichever response arrives first.
4. Tests cover out-of-order completions, same-window duplication, concurrent map safety, checkpoint crash, transient errors, 429/401/403, cancellation and no new scheduling after failure or target. `go test -race ./...` must pass. Do not enable concurrency by default unless controlled runs demonstrate lower total time without unacceptable quota or quality regressions.

## 6. GPU transcription benchmark (separate from selector)

1. Preserve the working CPU build and small model. Check official whisper.cpp CUDA build requirements, WSL driver/toolkit compatibility, available RAM/VRAM and disk; install/build in a separate path only after confirming requirements. Do not assume `nvidia-smi` alone means CUDA compilation is available.
2. Run CPU and CUDA with the identical small model, identical 16 kHz WAV, Portuguese language, full JSON/token timestamp flags, and comparable decoding settings. Measure conversion and inference separately; collect wall time, peak system RAM and VRAM, actual device used and complete output. Benchmark this source and a longer source. Keep actual model and build hashes.
3. Compare Portuguese proper names, missing/extra speech, word timestamp drift and resulting approved cuts against a human-checked sample. Verify the app's JSON parser receives usable token timestamps. Record failures and any changes to decoding or quality; do not equate synthetic sample speed with end-to-end speed.
4. If reliable and meaningfully faster, add explicit `cpu`/`cuda` backend configuration with a CPU fallback only on initialization failure and a clear status message; do not silently fall back after partial output or mask data errors. Preserve the CPU path and allow user override. Test absent GPU, missing libraries, memory exhaustion and cancellation. Benchmark smaller/quantized models as a separate variable, never simultaneously with a first GPU comparison.

## 7. Rendering and download

- Measure source download, audio conversion and each render before optimizing them. The reported case reused media, so downloading is not its demonstrated bottleneck. Validate reuse of both files independently and do not redownload valid data due to a partial prior run.
- Benchmark the same candidate, dimensions, captions and framing with current `libx264` and supported NVIDIA encoding, including initialization, output size, video/audio quality, caption synchronization, resource use and render time. Compare visually at comparable output quality; NVENC availability in WSL must be verified. Keep CPU fallback and existing ffprobe checks; do not introduce an encoder default based on GPU presence alone.
- Consider lower-resolution previews only after timing confirms render cost; require final export at requested resolution and quality. Limit concurrent renders to avoid oversubscribing CPU/GPU and disk. Reuse source decode only if measurements justify complexity and failure recovery remains per-cut.

## 8. Release gates and decisions

- Gate A: baseline report and complete instrumentation verified, including failure/cached cases.
- Gate B: multiple cuts and fast/full modes meet functional and recovery tests; compare human-rated quality and first-cut latency on the evaluation set. Keep full default until explicitly decided from evidence.
- Gate C: concurrency comparison demonstrates an improvement without unacceptable rate-limit failures; otherwise retain serial processing and document results.
- Gate D: GPU and encoder comparisons prove operational reliability and visual/transcription quality; otherwise retain CPU and document the result.
- Final checks: Go unit/integration/race tests, frontend embedded build, manually review each produced cut against source, verify timestamps and caption sync, inspect event logs for missing data and secrets. Report exact workloads, versions, measured distributions and remaining unknowns. Do not stop or duplicate a user's active job for these checks.
